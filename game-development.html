LOCAL TOOL / FRAME BUDGET

Every feature spends time somewhere.

A 60 FPS target gives only 16.67 ms for an entire frame. Budget early, profile on representative hardware, and treat CPU and GPU timelines as separate resources that can overlap or stall each other.

CURRENT ENGINEERING REFERENCES / 2026

Know the standards beneath the engines.

WebGPU

Modern web API for GPU rendering and general-purpose compute. The W3C specification remains in the Candidate Recommendation process in 2026, so implementation/version details should be checked.

W3C WebGPU ↗

Vulkan

Explicit cross-platform graphics/compute API where synchronization, memory management and pipeline construction are more directly controlled by the application.

Khronos Vulkan docs ↗

SDL3

Low-level cross-platform access to input, audio, windows and graphics integration—a useful reference point for understanding the platform layer beneath a custom engine.

SDL3 documentation ↗

Godot 4.x

Open-source engine reference for scenes/nodes, rendering, physics, scripting, import pipelines and editor tooling. Compare architecture choices rather than copying an engine wholesale.

Godot stable docs ↗

OpenXR

Cross-platform API family for XR application/runtime interoperability. Relevant if PyreFrame eventually targets immersive devices.

OpenXR registry ↗

PYREFRAME / ENGINE DIRECTION

A custom engine should solve a concrete problem.

The long-term PyreFrame direction is to keep platform/input, simulation, rendering, physics, audio, assets, tools and game logic behind explicit boundaries; make deterministic/testing surfaces first-class; and let higher-level Pyre Foundry tooling automate repetitive development work without owning unverifiable release decisions. That is a design direction, not a claim that a full Godot/Unreal-class engine exists today.
