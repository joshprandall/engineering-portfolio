What it is

Fit predictive functions from examples while keeping data separation, baselines, uncertainty, and generalization testing explicit.

This page separates the concept, implementation path, interactive experiment, evaluation criteria, failure modes, and sources so the topic can be studied without relying on a summary tile.

Core concepts

  • Features represent inputs; targets represent what the model is asked to predict.
  • A loss function turns prediction error into an optimization objective.
  • Training estimates model parameters from one dataset partition.
  • Validation guides model choice; the final test set estimates generalization after choices are frozen.
  • Baselines show whether model complexity is earning its cost.

Architecture / workflow

  1. Define the prediction target and success metric.
  2. Split data before tuning and prevent leakage across partitions.
  3. Train a simple baseline first.
  4. Fit candidate models and tune only on training/validation data.
  5. Evaluate once on held-out data, then monitor drift and calibration after deployment.

Technical foundations

  • Empirical risk minimization chooses parameters θ that minimize average loss (1/n)ΣL(fθ(xᵢ),yᵢ).
  • Regularization adds a complexity penalty to reduce overfitting.
  • Classification metrics such as precision, recall, ROC-AUC, PR-AUC, calibration error, and confusion matrices answer different questions.
  • Cross-validation reduces dependence on one arbitrary validation split when data size permits.

Evaluation checklist

  • Compare against naive and linear baselines.
  • Use metrics appropriate to class imbalance and decision cost.
  • Inspect calibration, subgroup performance, and error slices.
  • Repeat evaluation under realistic distribution shift.
  • Track data and model versions so results are reproducible.

Failure modes and limits

  • Data leakage can make a weak model look excellent.
  • A random split can hide temporal or group dependence.
  • High aggregate accuracy can conceal poor minority-class behavior.
  • Correlation learned from historical data may fail after the environment changes.

Practical build path

  1. Train a linear or tree baseline on a small labeled dataset.
  2. Add a held-out split and confusion-matrix analysis.
  3. Compare calibration and error slices across two model families.
  4. Add drift monitoring and retraining criteria only after the baseline is reproducible.

AUTHORED STUDY COMPANION / 3.2

Fit a classifier without leaking the test set

Prerequisites. Vectors, conditional probability, gradients, and the distinction between fitting and evaluation.

A binary logistic model assigns p(y=1|x)=sigmoid(wᵀx+b). Cross-entropy penalizes confident wrong predictions; its gradient averages x(p−y). Starting with zero weights predicts 1/2 for every example. A useful first check is whether training loss falls after a modest update, not whether the model looks sophisticated.

The companion generates 180 fictional two-feature observations with seed 7 and splits them into 100 training, 40 validation and 40 test examples before fitting anything. The scaler learns its mean and standard deviation from training data only. Even unsupervised preprocessing can leak information if it sees held-out observations. The test split is inspected after the training choices in this fixed demonstration; repeated tuning against it would invalidate its role.

Confusion-matrix rows are true classes and columns are predicted classes. Compare the model with the training-majority baseline. Accuracy on 40 synthetic test cases is evidence about this fixture, not a production estimate. To extend the experiment, create a separate evaluation cohort with a changed boundary and inspect which errors increase.

Extend the experiment

Change the data-generating coefficient or noise level in a copied function. Freeze the trained model, then measure the resulting error slice without refitting the scaler on the new cohort.

Check your reasoning: Where should the scaler learn its mean?
  1. All 180 rows — That lets held-out distribution information enter fitting.
  2. Training rows only — Correct. The fitted preprocessing is part of the training procedure.
  3. Test rows only — That directly conditions preprocessing on evaluation data.

GUIDED EVALUATION LAB / MACHINE LEARNING

Reproduce an imbalanced-classifier evaluation

This original, fictional device-alert classifier exercise demonstrates why accuracy alone is inadequate. It is a guided calculation, not a deployed model, measured research experiment, live simulator, or certification. Prerequisites: binary labels, fractions, and held-out evaluation.

Define and freeze the test contract

Positive means actionable alert. The test unit is one independent, synthetic device-window. A fictional held-out set contains 100 windows, including 12 positives. Assume the threshold was fixed before test labels were examined. Counts alone do not establish real-world independence, model calibration, statistical significance, drift resistance, or deployment readiness.

Synthetic held-out confusion matrix (100 device-windows)
Actual classPredicted positivePredicted negative
Positive (12)9 true positives3 false negatives
Negative (88)11 false positives77 true negatives

Derive, do not merely quote, the metrics

Prevalence: 12/100 = 12%. Precision: 9/(9+11) = 0.45. Recall: 9/(9+3) = 0.75. Specificity: 77/(77+11) = 0.875. Accuracy: (9+77)/100 = 0.86. Positive-class F1: 2(9)/(2(9)+11+3) = 0.5625. Balanced accuracy: (0.75+0.875)/2 = 0.8125.

Compare the baseline: an always-negative rule reaches 88% accuracy but detects none of the 12 positive windows (recall = 0). For a deliberately fictional decision-cost model, a false alert costs 2 effort units and a missed alert costs 20. The classifier costs 11(2)+3(20) = 82; the baseline costs 12(20) = 240. The assumed costs are not field measurements.

Replicate with Python 3 (standard library only)

Copy into a local Python file and execute it. This independently verifies arithmetic, not the provenance or quality of the fictional labels. Expected precision 0.4500, recall 0.7500, F1 0.5625, accuracy 0.8600, and costs 82 versus 240.

from fractions import Fraction
tp, fp, fn, tn = 9, 11, 3, 77
n = tp + fp + fn + tn
assert n == 100 and tp + fn == 12 and fp + tn == 88
metrics = {
    "precision": Fraction(tp, tp + fp),
    "recall": Fraction(tp, tp + fn),
    "specificity": Fraction(tn, tn + fp),
    "accuracy": Fraction(tp + tn, n),
    "f1": Fraction(2 * tp, 2 * tp + fp + fn),
}
metrics["balanced_accuracy"] = (metrics["recall"] + metrics["specificity"]) / 2
assert metrics["f1"] == Fraction(9, 16)
assert metrics["balanced_accuracy"] == Fraction(13, 16)
for key, value in metrics.items():
    print(f"{key}: {float(value):.4f}")
model_cost = 2 * fp + 20 * fn
baseline_cost = 20 * (tp + fn)
assert (model_cost, baseline_cost) == (82, 240)
print(f"synthetic costs: {model_cost} vs {baseline_cost}")

Four guided review questions

A. Baseline choice: Which system has higher accuracy? Which has higher recall? Is either sufficient to justify deployment?

Reveal baseline reasoning

The baseline has higher accuracy (88% versus 86%) but zero positive recall. The model has 75% recall and 45% precision; the artificial cost assumptions favor it (82 versus 240 units). Neither aggregate comparison establishes real deployment performance.

B. Counterfactual: If five additional false positives are observed and no other counts change, what is the new precision?

Reveal the recalculation

True positives remain 9 while false positives rise from 11 to 16. Precision = 9/(9+16) = 9/25 = 0.36; recall remains 9/12 = 0.75 under the stated fixed-count thought experiment.

C. Leakage: What goes wrong if the analyst optimizes the decision threshold using these 100 test labels and reports the same F1 as independent test performance?

Reveal the evaluation correction

Threshold choice has overfit to the supposed test set. Train and select the threshold using training/validation data, freeze the pipeline, and evaluate once on an untouched test partition. Group by device and respect time boundaries where related windows could leak across partitions.

D. Evidence: What additional evidence is required before claiming the model reduces operational risk?

Reveal three evidence families

Document representative sampling and independently adjudicated labels; uncertainty intervals and subgroup/temporal performance; plus the real alert burden, miss costs, latency, monitoring and drift response. Record dataset and code versions, seed where used, split identifiers, environment, and retention policies.

Review and provenance boundaries

For a credible real study, publish a privacy-safe versioned data contract, label definition, split specification, evaluation script and reproducible result manifest. Never expose customer or device identifiers in a teaching dataset. The computations here cannot validate a model that does not exist.
