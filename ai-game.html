What it is

Choose actions inside formal game rules using search, heuristics, planning, learned policies, or combinations of these methods.

This page separates the concept, implementation path, interactive experiment, evaluation criteria, failure modes, and sources so the topic can be studied without relying on a summary tile.

Core concepts

  • A game state and legal-action generator define what moves are possible.
  • Search explores future action sequences.
  • Evaluation functions estimate states when exhaustive search is impossible.
  • Minimax models adversarial turn-taking; pruning avoids branches that cannot change the result.
  • Monte Carlo tree search estimates promising actions through repeated simulated play.

Architecture / workflow

  1. Implement legal state transitions before adding intelligence.
  2. Create a deterministic baseline such as random or heuristic play.
  3. Add search with a fixed depth or simulation budget.
  4. Benchmark against the baseline across many games.
  5. Inspect illegal moves, repeated states, timing, and edge cases.

Technical foundations

  • Minimax alternates MAX and MIN layers to propagate utility values.
  • Alpha-beta pruning preserves the minimax result while skipping provably irrelevant branches.
  • MCTS balances exploration and exploitation while building a partial search tree.
  • Learned policies/value functions can replace or guide hand-written heuristics.

Evaluation checklist

  • Win/draw/loss rate against fixed opponents.
  • Illegal-move rate must be zero.
  • Nodes searched, time per move, and memory.
  • Performance by opening/state family rather than only aggregate win rate.
  • Determinism and reproducibility under fixed seeds.

Failure modes and limits

  • A strong evaluation function can still violate rules if state transitions are wrong.
  • Benchmark opponents may be too weak or too similar.
  • Search time can explode with branching factor.
  • Learning systems can exploit simulator bugs instead of learning intended strategy.

Practical build path

  1. Implement minimax on a tiny deterministic game tree.
  2. Add alpha-beta pruning and count visited nodes.
  3. Integrate a legal-move engine for a real game.
  4. Benchmark a heuristic or learned evaluator against fixed search baselines.

AUTHORED STUDY COMPANION / 3.5

Solve a small game exactly before learning it

Prerequisites. Turn-based games, terminal states and dynamic programming.

In this normal-play subtraction game, a player removes one or two stones and the player taking the last stone wins. Position zero is losing for the player to move. A positive position is winning if any legal move leads to a losing position for the opponent. The companion builds this table from small positions upward.

For five stones, taking two leaves three, a losing position. This is exact dynamic programming for a fully known game, not an RL agent and not a change to either protected portfolio game. It provides a clean baseline for a later learned policy: compare decisions against the solved state table, including losing states where no winning move exists.

Extend the experiment

Train a small policy against the solved opponent and report agreement by state. Do not score an arbitrary move in a losing state as a missed guaranteed win.

Check your reasoning: A losing state means:
  1. No legal move exists in every case — Three stones has legal moves but is losing.
  2. No forced win against optimal play under the rules — Correct. Every legal move gives the opponent a winning position.
  3. The program crashed — It is a valid game-theoretic result.

This is an explained self-check, not a certification of mastery.
