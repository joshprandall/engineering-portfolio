Defensive detection lab: correlating sign-in evidence

Guided, reproducible exercise; not a live monitor. These twelve events are entirely synthetic; accounts are fictitious and IPs use documentation-only ranges. This experiment demonstrates detection reasoning, not an incident finding or performance guarantee. No real telemetry, secrets or network operations are involved.

Specify a falsifiable hypothesis

Rule: at each successful authentication, count earlier failed attempts from the same account and source address during the preceding 600 seconds, inclusive. Produce a signal when the count is at least three. The exact account, source, outcome, time boundary, failure threshold and ordered events form the test contract. A threshold match is not proof that a password was guessed or a session compromised. NAT, shared IPs, forgotten passwords and gaps in log ingestion are alternative explanations.

Documentation-only source addresses derive from RFC 5737 examples. No records describe real traffic. All timestamps below are UTC.

Independently rerun in Python 3

This dependency-free reference implementation consumes exactly the fixture above. Run locally in a disposable Python environment. The terminal must show a single ALERT for alex followed by alerts=1. The script only analyzes embedded test data; it cannot connect to your accounts or infrastructure.

from datetime import datetime
from io import StringIO
import csv

CSV = """timestamp,account,source,result
2026-11-10T08:00:00Z,alex,192.0.2.10,failed
2026-11-10T08:01:00Z,alex,192.0.2.10,failed
2026-11-10T08:02:00Z,alex,192.0.2.10,failed
2026-11-10T08:03:00Z,alex,192.0.2.10,success
2026-11-10T08:04:00Z,alex,192.0.2.11,success
2026-11-10T08:08:00Z,pat,198.51.100.5,failed
2026-11-10T08:14:00Z,pat,198.51.100.5,failed
2026-11-10T08:15:00Z,pat,198.51.100.5,success
2026-11-10T08:20:00Z,kim,203.0.113.8,failed
2026-11-10T08:21:00Z,kim,203.0.113.8,failed
2026-11-10T08:22:00Z,kim,203.0.113.8,failed
2026-11-10T08:35:00Z,kim,203.0.113.8,success"""
events = list(csv.DictReader(StringIO(CSV)))
for e in events:
    e["time"] = datetime.fromisoformat(e["timestamp"].replace("Z","+00:00"))
count = 0
for success in events:
    if success["result"] != "success": continue
    failures = [
        f for f in events
        if f["result"] == "failed"
        and f["account"] == success["account"]
        and f["source"] == success["source"]
        and 0 <= (success["time"] - f["time"]).total_seconds() <= 600
    ]
    if len(failures) >= 3:
        count += 1
        print("ALERT", success["account"], success["source"], success["timestamp"], "failures="+str(len(failures)))
print("alerts="+str(count))

Engineering interpretation and response evidence

The observed signal supports only this rule on this synthetic fixture. The two-failure and expired-window cases are negative controls: any detector that reports those as positive violates the rule. Before triaging real data, validate timestamp synchronization and event completeness, compare account/device baselines, correlate MFA and conditional-access outcomes, investigate IP sharing and legitimate retries, and record false-positive dispositions. For authorized investigations, preserve original read-only exports with SHA-256, time range and timezone, normalized detection query, rule version, analyst rationale, chain of handling and appropriately restricted retention; minimize personal identifiers when sharing.

For context, review MITRE ATT&CK T1110 (Brute Force) and NIST SP 800-61 Rev. 3 (2025 incident response). This lab is not a certification of either framework or a claim of affiliation.

Guided exercises and explanations

Which event meets the threshold?

The 08:03 UTC success for alex from 192.0.2.10 is preceded at 08:00, 08:01 and 08:02 by exactly three failures from that same account and source.

Why does pat not trigger?

Pat has only two qualifying failures at 08:08 and 08:14 before the 08:15 success; the specified threshold is three. Counting all users together would be a defect.

Why is kim a negative time-boundary control?

Kim's last failed attempt was at 08:22, thirteen minutes before the 08:35 success. Even that most recent failure is outside 600 seconds. Counting historical failures without a time window would be incorrect.

What evidence would you need before declaring an incident?

Confirm identity and clock provenance, completeness of logs, baseline legitimate retries, shared-source behavior, MFA and policy outcomes, device/session context and corroborating activity. An alert is a reason to investigate, not proof of malicious intent or compromise.
