What it is

Place a model inside a bounded observe-plan-act loop so it can select tools, maintain state, recover from errors, and request approval for consequential actions.

This page separates the concept, implementation path, interactive experiment, evaluation criteria, failure modes, and sources so the topic can be studied without relying on a summary tile.

Core concepts

  • State records what the agent currently knows about the task and environment.
  • Planning selects a next action or decomposes work into smaller steps.
  • Tools connect model reasoning to deterministic code or external systems.
  • Observation feeds tool results back into the loop.
  • Approval gates separate suggestions from actions that affect people, systems, money, data, or external communication.

Architecture / workflow

  1. Receive a task and convert it into an explicit contract: goal, constraints, tools, budget, and stop conditions.
  2. Observe current state and available evidence.
  3. Choose one bounded action and validate its parameters.
  4. Execute through an authorized tool, capture the result, and update state.
  5. Stop, recover, or request human approval when confidence, authority, cost, or safety boundaries are exceeded.

Technical foundations

  • A useful abstraction is a state machine over (state, observation, action, result).
  • Idempotent tools and replayable traces make recovery safer.
  • Budgets can bound steps, time, tokens, external requests, or financial cost.
  • Permission checks should be enforced outside the language model whenever possible.

Evaluation checklist

  • Task completion rate on reproducible scenarios.
  • Tool-call validity and parameter accuracy.
  • Recovery success after injected failures.
  • Rate of unnecessary or unauthorized actions.
  • Trace completeness: can another person reconstruct why each action occurred?

Failure modes and limits

  • Long action chains compound small errors.
  • A model may call the right tool with the wrong parameter.
  • Untrusted tool output can influence later reasoning.
  • Hidden state makes failures hard to reproduce.
  • Over-broad permissions convert reasoning mistakes into real-world side effects.

Practical build path

  1. Start with one deterministic tool and a tiny state machine.
  2. Add structured observations, logging, and explicit stop conditions.
  3. Add more tools only with per-tool authorization and validation.
  4. Introduce approval gates, budgets, replay, rollback, and adversarial testing before external actions.
